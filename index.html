Tool · Agent · User benchmark

What τ-bench actually measures
— and what it quietly doesn't

τ-bench (Sierra, 2024) tests whether an LLM can act as an enterprise customer-service agent: talk to a (simulated) customer, follow a written policy, call domain tools, and leave the database in exactly the right state. It is graded not on what it says, but on what it changed. This page builds the correct mental model, then shows where recent work says the measurement breaks.

2 domains · retail + airline 165 hand-authored tasks graded on final DB state reliability metric: pass^k

The mental model (your 1 · 2 · 3, sharpened)

You had the right instinct. Here it is pinned down against the paper.

① what it is NOT

Not a shopping assistant

The agent is not on the customer's side. It is not trying to find the cheapest milk or the fastest delivery. There is no optimization over price or time for the user at all.

In fact the human customer is itself an LLM — the user simulator — reading a hidden script of what it wants.

② what it IS

The enterprise's back-office agent

It is Amazon's / the airline's agent. Its job: check whether a return / exchange / cancellation / rebooking is allowed under policy, and if so, write that one change to the company database.

Sometimes the correct answer is to do nothing to the DB — just answer a question. 29 of the 165 tasks require no database write at all (9 need no tool calls whatsoever). You were right about that.

③ the problem it poses

Mostly: follow if-this-then-that

Each task is authored so the policy admits exactly one correct set of writes. So the core skill is reading rules and applying them in order — closer to executing a deterministic policy than to open-ended planning.

That's the strength (objective grading) and the critique (it's narrow). More below.

One correction to your model. You pictured "the database is written for one user and any conflicts are resolved at the database." τ-bench has no concurrency at all — one user, one session, one fixed snapshot of the DB, replayed deterministically. There are no competing writes, no other agents, no contention. That absence is exactly the gap the lab's serializability work aims at.

How one episode runs

PLAYER A

User simulator

An LLM given a hidden instruction (identity, intent, preferences). Reveals info one line at a time; never dumps the whole goal.

PLAYER B

The agent (under test)

Gets the policy document as its system prompt + a set of tools. Must authenticate the user, follow rules, confirm before writes.

WORLD

Tools + database

Read tools (non-mutating) and write tools (mutating) operate on a realistic DB of users, orders, products / flights.

JUDGE

Reward at the end

No human, no LLM judge. A rule compares the final DB to a gold DB and checks required strings.

The grading rule (this is the load-bearing detail)

At the end of the conversation, reward is a product of two binary checks:

reward = r_action × r_output ∈ {0, 1}

r_action

The final database must be byte-identical to the single annotated ground-truth outcome DB. The gold answer is literally "this exact set of write calls, nothing more." Read calls and the wording of the chat are ignored.

r_output

The agent's messages must contain the required output strings (e.g. a refund amount "54.04") as substrings. Plain keyword match — not semantic judging.

The authors' own caveat: reward = 1 is necessary but not sufficient. An agent can write the right row to the DB without getting the policy-required user confirmation and still score 1. The grader sees the destination, not the journey.

Why a reliability metric, not accuracy

pass^k ("pass-hat-k") = the probability that a task succeeds in all k independent trials, averaged over tasks. It rewards consistency, not luck. This is the paper's punchline:

~61%
GPT-4o, retail, pass^1 (solve it once)
~25%
Same model, retail, pass^8 (solve it 8/8 times)
~$200
cost of one retail trial in the 2024 paper (long policy prompt dominates)

Frontier agents look competent once and unreliable repeatedly — the gap between "can" and "can be trusted to."

A real task, end to end

Retail task #0 (you can open it live in the explorer):

hidden user instruction

"You are Yusuf Rossi in 19122. You received order #W2378156 and wish to exchange the mechanical keyboard for a similar one but with clicky switches, and the smart thermostat for one compatible with Google Home instead of Apple HomeKit. If there is no keyboard that is clicky, RGB, full-size, you'd go for no backlight. You are detail-oriented and want everything addressed in one go."

gold answer = exactly these calls 
find_user_id_by_name_zip(first_name="Yusuf", last_name="Rossi", zip="19122")   › read
get_order_details(order_id="#W2378156")                                       › read
get_product_details(product_id="1656367028")                                  › read
get_product_details(product_id="4896585277")                                  › read
exchange_delivered_order_items(order_id="#W2378156",
   item_ids=["1151293680","4983901480"],
   new_item_ids=["7706410293","7747408585"],
   payment_method_id="credit_card_9513926")                                   › the ONE mutating call

The agent must discover all those IDs by reading, reason about variant options against the policy, get confirmation, then make one write that matches gold exactly. Wrong item id, extra write, or skipped item ⇒ reward 0.

τ²-bench's key finding: take the user away and hand the agent all the tools ("No-User" mode) and gpt-4.1 jumps ~0.34 → ~0.73 on telecom. Coordinating with a human is the bottleneck, not raw reasoning. Sierra later shipped τ³-bench (knowledge + voice), absorbing many community task fixes.

Where the cracks are — what recent work establishes

Four 2025–26 papers, all circling one nerve: the measurement may not mean what the leaderboard implies.

SABER · Small Actions, Big Errors

Failure hides in the mutating steps

A deviation on a state-changing action cuts odds of success by up to ~92–96%; deviations on read actions barely matter. Protect the few mutating steps and most reliability returns. Also ships τ-Bench Verified — and finds the original gold annotations had real errors.

Full SABER reading →
Lost in Simulation · Seshadri et al.

LLM users aren't real users

Swap the simulator LLM and agent success swings up to 9 points. Simulated evals are miscalibrated — over-rating on moderate tasks, under-rating on hard — and disadvantage e.g. AAVE speakers. The "user" is an unreliable proxy.

arXiv 2601.17087

Mind the Sim2Real Gap · Zhou et al.

Simulated users are "easy mode"

First full τ-bench run with 451 real humans. LLM users are too cooperative, too uniform, never frustrated — inflating agent success vs. humans. And a bigger base model does not make a more faithful simulator. arXiv 2603.11245

LMs Don't Know What You Want · Balepur et al. (ACL)

Synthetic eval misses real failures

For deep-research agents: synthetic users + LLM judges show wins, but interviewing real users surfaced 9 personalization failures the judges entirely missed. Same disease, different domain. arXiv 2603.16120

The through-line. τ-bench made grading objective by replacing human judgment with a database diff. That was the breakthrough and the catch: it grades the destination state, assumes a single correct path, and leans on an LLM pretending to be a customer. Every critique above pulls one of those three threads.
